# System Blueprint & Data Schemas - CrowdPulse / OmniVenue

> **Project:** Unified Mega-Event Capacity, Transit & Venue Orchestration System  
> **Architecture:** MERN (MongoDB, Express, React, Node.js) + Socket.io + Pure JS Optimization & Forecasting Services  
> **Status:** Phase 1 (Blueprint) - Schemas & Interfaces Finalized

## 1. Domain Entities & Mongoose Data Schemas

### 1.1 `Zone` Schema
Represents a geographical district, venue cluster, or transit hub within the event perimeter.

```typescript
interface IZone {
  _id: string; // e.g. "zone-downtown", "zone-stadium-north"
  name: string;
  category: "venue_cluster" | "transit_hub" | "hospitality" | "commercial" | "buffer";
  geoBoundary: {
    type: "Polygon" | "Point";
    coordinates: number[][] | number[]; // [lng, lat] for Leaflet
  };
  totalCapacity: {
    venue: number;       // total spectator/attendee max limit
    transit: number;     // max transit handling per hour
    hospitality: number; // dining & stay capacity
  };
  liveMetrics: {
    currentVenueOccupancy: number;
    currentTransitPressure: number; // 0.0 to 1.0 ratio
    currentHospitalityOccupancy: number;
    compositeStressScore: number;   // 0 to 100 calculated index
    status: "normal" | "elevated" | "warning" | "critical";
    lastUpdated: Date;
  };
  metadata: {
    accessibilityScore: number;
    transitConnectedZoneIds: string[];
  };
}
```

### 1.2 `Venue` Schema
Specific indoor/outdoor arenas, halls, or designated event stadiums located within a zone.

```typescript
interface IVenue {
  _id: string;
  name: string;
  zoneId: string; // Foreign key -> Zone._id
  category: "stadium" | "exhibition_hall" | "fan_park" | "conference_center";
  maxCapacity: number;
  currentOccupancy: number;
  ingressRatePerMin: number;
  egressRatePerMin: number;
  scheduledEvents: {
    eventId: string;
    name: string;
    startTime: Date;
    endTime: Date;
    ticketedAttendance: number;
    status: "upcoming" | "in_progress" | "concluded";
  }[];
}
```

### 1.3 `TransitEdge` Schema
Physical or multi-modal transit links between zones (Metro, Shuttle, Bus, Pedestrian corridor).

```typescript
interface ITransitEdge {
  _id: string;
  fromZoneId: string;
  toZoneId: string;
  mode: "metro" | "shuttle_bus" | "pedestrian_walkway" | "rideshare";
  distanceMeters: number;
  baseTravelTimeMinutes: number;
  maxThroughputPerHour: number;
  liveStatus: {
    currentFlowPerHour: number;
    currentTravelTimeMinutes: number;
    utilizationRate: number; // currentFlow / maxThroughput (0.0 to 1.5+)
    congestionLevel: "free_flow" | "moderate" | "heavy" | "gridlock";
    isActive: boolean;
  };
}
```

### 1.4 `VisitorFlowSnapshot` Schema
Periodic time-series state records saved to MongoDB for trend analysis, historical replay, and post-event analytics.

```typescript
interface IVisitorFlowSnapshot {
  timestamp: Date;
  simulatedTime: Date;
  globalMetrics: {
    totalActiveVisitors: number;
    systemAverageStressScore: number;
    activeAlertsCount: number;
  };
  zoneSnapshots: {
    zoneId: string;
    occupancy: number;
    capacity: number;
    stressScore: number;
    forecastedStressNext1hr: number;
  }[];
  edgeSnapshots: {
    edgeId: string;
    flowPerHour: number;
    utilizationRate: number;
  }[];
}
```

### 1.5 `Alert` Schema
Actionable breach notifications generated automatically by the rule engine.

```typescript
interface IAlert {
  id: string;
  timestamp: Date;
  zoneId: string;
  type: "capacity_breach" | "transit_bottleneck" | "forecast_surge" | "evacuation_risk";
  severity: "info" | "warning" | "critical";
  title: string;
  message: string;
  metrics: {
    currentVal: number;
    thresholdVal: number;
    unit: string;
  };
  recommendedActionId?: string; // Links to IReallocationRecommendation
  isAcknowledged: boolean;
}
```

### 1.6 `ReallocationRecommendation` Schema
Action recommendations generated by the deterministic optimization solver.

```typescript
interface IReallocationRecommendation {
  id: string;
  generatedAt: Date;
  targetAudience: "organizer" | "visitor";
  category: "transit_reroute" | "alternate_zone" | "staggered_departure" | "surge_gate_control";
  sourceZoneId?: string;
  targetZoneId?: string;
  title: string;
  description: string;
  impactEstimation: {
    estimatedStressReliefPct: number;
    affectedVisitorCount: number;
    etaChangeMinutes: number;
  };
  suggestedActionPayload: {
    shuttleDispatchDelta?: number; // e.g. +4 buses to Route B
    entryGateThrottlePct?: number; // e.g. -20% inflow rate
    recommendedArrivalWindow?: string; // e.g. "17:45 - 18:15"
  };
}
```

## 2. In-Memory Live State (Node.js Tick Engine)

The simulation engine maintains the hot state in memory and broadcasts deltas every tick ($T_{tick} = 5s$).

```typescript
interface ILiveState {
  simulatedClock: {
    currentTime: Date;
    speedMultiplier: number; // e.g. 1x, 5x, 10x
    isPaused: boolean;
  };
  whatIfOverrides: {
    eventStartTimeDeltas: Record<string, number>; // eventId -> offset in minutes
    transitCapacityDeltas: Record<string, number>; // edgeId -> throughput multiplier
    demandSurgeMultiplier: number; // global crowd multiplier (0.5 to 2.0)
  };
  zones: Map<string, IZone>;
  venues: Map<string, IVenue>;
  transitEdges: Map<string, ITransitEdge>;
  activeAlerts: IAlert[];
  activeRecommendations: IReallocationRecommendation[];
  recentSnapshotsWindow: IVisitorFlowSnapshot[]; // rolling window for forecasting
}
```

## 4. WebSocket (Socket.io) Event Contract

| Event Name | Direction | Payload | Description |
| :--- | :--- | :--- | :--- |
| `live:tick` | Server $\rightarrow$ Client | `{ simulatedTime, zones, edges, alerts, recommendations }` | Main real-time heartbeat (every 5-10s) |
| `scenario:update` | Client $\rightarrow$ Server | `{ surgeMultiplier, eventDeltas, transitDeltas }` | Organizer drags what-if sliders |
| `scenario:reset` | Client $\rightarrow$ Server | `{}` | Reverts simulator to baseline scenario |
| `visitor:requestRoute` | Client $\rightarrow$ Server | `{ fromZoneId, toZoneId, preference: "fastest" \| "least_crowded" }` | Visitor requests optimal path |
| `visitor:routeResponse` | Server $\rightarrow$ Client | `{ pathZoneIds, estimatedMinutes, crowdednessRating, alternatePath }` | Guidance response to visitor |
